# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause or root-cause section, read against the repro-evidence block's observed behavior, error messages, and artifacts. | The plan names a specific cause, and that cause explains the behavior the repro evidence actually shows. If the plan's stated cause contradicts what the repro evidence demonstrates (e.g., claims a missing import when the repro shows a logic error), or if the plan ignores the repro evidence entirely and diagnoses from the issue title alone, it fails. A plan that honestly says "cause is uncertain" and explains what the repro evidence narrows it to passes. | required |
| scope-bounded | The plan's in-scope and not-in-scope statements, the files or areas named, and the approach section. | The plan describes one bounded change: it names the specific files or functions it will touch and draws a line around what it will not change. If the plan includes drive-by refactors, unrelated cleanups, dependency upgrades, or changes beyond what the diagnosis requires, it fails. Adding a necessary test file alongside the fix is in scope. If no boundary is stated at all, it fails. | required |
| plan-executable | The plan's approach section, files named, and order of work, read against the repo-facts block. | A stranger who has the repo cloned could start executing the plan without asking the author anything. The plan names the files to change, describes the concrete edits or additions (not just "fix the bug"), and states an order of work if more than one file is involved. If the plan says only "add a check" without saying where in the code or what the check compares, it fails. | required |
| test-plan-decisive | The plan's test plan or verification section, read against the repro-evidence block's steps and observed artifacts. | The test plan names at least one observable check that would distinguish "fixed" from "still broken." It maps onto the repro evidence's steps: it re-runs those steps (or a subset) and states the expected output after the fix, which must differ from the repro evidence's observed output. A test plan that says only "run the tests" or "verify it works" without naming what to observe fails. | required |
| honesty-about-unknowns | The plan's risks, unknowns, or deviations section, read against any claims of certainty in the approach. | The plan does not present uncertain assumptions as established facts. If the plan claims a specific root cause without evidence pinning it, or asserts that a fix will have no side effects without stating why, it fails. Stating "I believe X because the repro shows Y, but Z is a risk" passes. A plan with no risks or unknowns section fails unless the change is trivially scoped (a one-line typo fix or a single guard clause with an existing test). | required |
| comment-thread-aware | The plan comment text, read against the thread highlights in the package and the repo-facts block's stated templates, contributing policy, and AI-use disclosure requirements. | The plan comment addresses the specific issue (not boilerplate), references or builds on relevant thread context (prior discussion, maintainer signals), and follows the repo's stated conventions. If the repo requires AI-use disclosure and the comment does not disclose, it fails. If the comment ignores a maintainer's explicit direction in the thread highlights (e.g., maintainer said "don't change the API" and the plan changes the API), it fails. A comment that could be pasted on any issue without modification fails. | required |
| names-repro-evidence | The plan's diagnosis and test plan, read for references to the repro-evidence block's specific outputs, commands, or artifacts. | The plan explicitly references at least one concrete artifact from the repro evidence (a specific error message, a status code, a command output, a database state) rather than restating the issue description in its own words. This grounds the plan in observed behavior rather than assumed behavior. | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check fails. Unclear on any required check counts as fail. Preferred checks never change the verdict; they rank accepted plans.
